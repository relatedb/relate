# ADR-0484: Speak Bolt 5.4 beside 4.4

Status: Proposed

Claim: 1765fee307f6686d207cd8ee195092dc4582770c

## Context

The Bolt server (ADR-0057) is CypherLite's remote transport for official
Neo4j drivers — a transport, not Neo4j parity. It speaks Bolt 4.4 only:
the handshake answers `00 00 04 04` when a proposal covers 4.4
(ADR-0303), auth rides in HELLO (ADR-0126), and `docs/api/bolt/spec.md`
lists "Bolt 5+ logon" under Not supported.

ADR-0303 corrected the handshake and left the 5.x question open on
purpose. `docs/api/bolt/compatibility.md`'s deferred item F-06 records
the follow-up: *Bolt: manifest-v1 handshake (`00 00 01 FF`) as part of a
Bolt 5.x negotiation decision*, covered today by
`surfaces/cypherlite-bolt/tests/compat/scripts/baseline/negotiation-6-manifest-then-44.bolt`.
This ADR is that decision.

The clients have moved. The official Python driver (neo4j 6.3.1,
wire-captured 2026-11-02, identical to its `get_handshake()` constants)
proposes, in client order: `00 00 01 FF` (the manifest-v1 marker),
`00 08 08 05` (Bolt 5.8, range 8 — 5.0 through 5.8), `00 02 04 04`
(Bolt 4.4, range 2 — 4.2 through 4.4) and `00 00 00 03` (Bolt 3).
Against CypherLite it negotiates 4.4, the oldest dialect it proposes
that we speak; everything the 5.x line added for drivers — LOGON/LOGOFF,
the notifications options, the telemetry opt-out hint — stays invisible.

A live probe against `neo4j:2026.09-community` (Docker, 2026-11-02)
pinned what this decision rests on: the multi-version negotiation
replies, the 5.4 HELLO field contract, LOGON/LOGOFF and their states,
TELEMETRY, the notifications option failures, and the manual's 5.0
element-id and DateTime structure changes. The compat corpus (ADR-0304)
is the vehicle that pins CypherLite's answers to all of it.

## Decision

The server offers **Bolt 4.4 and Bolt 5.4** — no intermediate minor,
nothing newer — and the 5.4 session follows the probed Neo4j 2026.09
behavior:

1. **Offered version set.** The spoken set is {4.4, 5.4}, the two reply
   forms `00 00 04 04` and `00 00 04 05`. No 5.0–5.3: the 5.x minors are
   cumulative (5.1 LOGON/LOGOFF, 5.2 notifications options, 5.3
   `bolt_agent`, 5.4 `TELEMETRY`), so each extra minor is another pinned
   compat surface that funnels through the same 5.4 code paths, and the
   ranges real drivers send (`00 08 08 05`) already cover 5.4. Nothing
   past 5.4: 5.6 renames the notifications keys, 5.7 adds the manifest
   handshake, 5.8 adds LOGON SUCCESS `advertised_address` — none of it
   is probe-pinned. Moving the ceiling is a new probe plus a new ADR.

2. **Multi-version reply rule, as probed.** The four proposals are read
   in client order; the **first proposal covering a spoken version
   decides the reply**. Neo4j 2026.09 answers 4.4 to a 4.4-first set and
   5.4 to a 5.4-first set — the client's first supported proposal wins,
   not the server's newest version. A proposal `00 RR mm MM` covers
   spoken version `v = M.m` when `MM = M` and `mm - RR <= m <= mm`, the
   subtraction saturating at 0 (ADR-0303's rule generalized from its
   4.4-only form; a range never spans majors, and with one spoken minor
   per major a covering proposal names exactly one spoken version). The
   reply is `00 00 mm MM`. When no proposal covers a spoken version the
   reply is `00 00 00 00` and the connection closes without reading
   further, inside the same ADR-0141 deadline (ADR-0303's no-cover
   close and deadline, unchanged). The manifest marker `00 00 01 FF`
   keeps ADR-0303's manifest-never-match answer: it never matches —
   the manifest-v1 handshake is not implemented
   (F-06, below) — and a version proposal beside it is answered plainly,
   so the official driver's set above skips the marker, covers 5.4 with
   its range proposal, and negotiates 5.4. The rule is the probed one;
   answers differ from Neo4j only where the spoken sets do — a
   5.3-exact-first set gets 5.3 from Neo4j and 5.4 from us, whose next
   proposal covers 5.4.

3. **A 5.x HELLO ignores auth fields and `patch_bolt`.** The 5.x HELLO
   extra must carry a non-null `user_agent` and a `bolt_agent` map of
   string keys and string values (mandatory since 5.3); anything else
   fails `Neo.ClientError.Request.Invalid` with the probed field
   messages. `scheme`, `principal` and `credentials` in a 5.x HELLO are
   silently ignored — Bolt 5.1 removed HELLO auth, and the probed Neo4j
   answers plain SUCCESS while the session stays *unauthenticated* (a
   following RUN fails in the AUTHENTICATION state) — and `patch_bolt`
   is silently ignored with no acknowledgment key (removed after 4.4;
   there is no patch negotiation at 5.x). The 4.4 HELLO keeps its
   ADR-0126 auth gate and ADR-0329 patch negotiation unchanged.

4. **LOGON carries the ADR-0126 auth.** At 5.1+ the credential check
   moves from HELLO to LOGON (`0x6A`); LOGOFF (`0x6B`) returns the
   session to the AUTHENTICATION state. LOGON accepts the two schemes
   ADR-0126 defines: `basic` — `principal` + `credentials` matching the
   resolved credential (`--auth` flag, then `CYPHERLITE_AUTH`, then the
   generated token), the verified principal forwarded engine-ward
   (ADR-0273) — and `none`, the explicit no-auth scheme, which
   authenticates only under `--auth none` (under which every LOGON
   succeeds, as every 4.4 HELLO does today). Any other scheme, or a
   mismatched `basic` token, fails
   `Neo.ClientError.Security.Unauthorized` and the connection is
   DEFUNCT — closed with nothing after it answered, per the 5.1 state
   table; the ADR-0139 guessing delay travels with the credential check.
   Success answers SUCCESS `{}`.

5. **Telemetry: opted out, still answered.** The 5.x HELLO SUCCESS adds
   `telemetry.enabled: false` to the `hints` map, beside ADR-0312's
   `connection.recv_timeout_seconds`: the server collects nothing, and
   the hint tells drivers not to send `TELEMETRY` (`0x54`, `api`
   Integer). A client that sends one anyway still gets SUCCESS `{}` —
   the manual requires the server to accept it — and nothing is
   recorded. An out-of-range `api` fails
   `Neo.DatabaseError.General.UnknownError`, a non-Integer `api` fails
   `Neo.ClientError.Request.Invalid` (the probed shapes; the corpus pins
   the messages).

6. **Element ids: the engine helpers; `None` is a typed error.** Bolt
   5.0 appended element-id fields to the graph structures — Node `0x4E`
   `[id, labels, properties, element_id]`, Relationship `0x52` `[id,
   start, end, type, properties, element_id, start_node_element_id,
   end_node_element_id]`, UnboundRelationship `0x72` `[id, type,
   properties, element_id]`; the integer ids stay. The strings come from
   the engine's `node_element_id` / `rel_element_id` helpers
   (`cypherlite-core/src/namespace.rs`, exported by the `cypherlite`
   crate) against the session's graph namespace (ADR-0116 §7) — the one
   source `elementId()` and the load surface already read; the server
   never builds an element-id string a second way. The helpers return
   `None` exactly for the `system` namespace, which has no element-id
   segment; a 5.x encoder hitting `None` fails with a typed error — the
   engine `elementId()` precedent, "elements of this namespace have no
   element ids" — never a fabricated id, a silent `neo4j` segment, or a
   panic.

7. **The fixed DateTime structures.** At 5.x the Bolt 5.0 forms are
   unconditional in both directions: an offset datetime is `0x49`
   DateTime `[UTC epoch seconds, nanoseconds, tz_offset_seconds]`, a
   zone datetime is `0x69` DateTimeZoneId `[UTC epoch seconds,
   nanoseconds, tz_id]` — the ADR-0329 utc-patch forms with no patch to
   negotiate, parameters and results alike. The legacy `0x46`/`0x66`
   (removed after 4.4) are rejected as parameters on a 5.x connection
   and never emitted. Every other temporal structure (ADR-0325) is
   unchanged.

8. **The notifications filter keys.** HELLO, BEGIN and auto-commit RUN
   extra accept the Bolt 5.2 options `notifications_minimum_severity`
   (String) and `notifications_disabled_categories` (List<String>) — the
   5.4-era spellings; the 5.6 rename is not offered. They filter the
   ending summary's `notifications` list (ADR-0363): entries below the
   named minimum severity and entries in a listed category are dropped,
   and the special severity `OFF` drops the whole list. The severity
   value set is `INFORMATION`, `WARNING`, `OFF`; category entries are
   free strings — the engine's categories are ADR-0363's `PERFORMANCE`,
   `UNRECOGNIZED`, `DEPRECATION`, and a filter naming one of Neo4j's
   wider set filters nothing rather than failing a legal driver value. A
   wrong-typed value or an unknown severity fails
   `Neo.ClientError.Request.Invalid`, as probed. A statement's keys
   override the HELLO's; `null` falls back to it. ADR-0363 derives
   notifications only for `EXPLAIN`/`PROFILE`, so plain runs have
   nothing to filter.

## Alternatives considered

- **Stay 4.4-only.** Nothing to implement, and every current driver
  still proposes 4.4, so nothing breaks. Rejected: a transport's job
  (ADR-0057) is that official drivers connect speaking a current
  dialect; against CypherLite the newest drivers fall back to the oldest
  dialect they still propose, with no LOGON flow, no notifications
  options and no telemetry hint — and F-06's follow-up, already deferred
  once by ADR-0303, would stay open with no owner. The probe that makes
  5.4 safe to offer is done.

- **Drop 4.4 and offer 5.4 only.** One dialect, one set of encoders.
  Rejected: the pinned compat corpus, cypher-shell and every client that
  proposes 4.4 or a 4.x range would get `00 00 00 00`. ADR-0126,
  ADR-0177, ADR-0272 and ADR-0329 pin 4.4 behavior real clients still
  exercise; 4.4 leaves only with evidence that no client of ours
  proposes it.

- **Offer every 5.x minor, 5.0 through 5.4.** Maximal compatibility —
  Neo4j answers any covered minor. Rejected: five offered versions are
  five compat surfaces to pin and keep, for one capability set — the
  minors are cumulative and the ranges real drivers send already select
  5.4. Only a client proposing an exact lower minor and nothing else we
  speak would notice, and the honest answer to it is `00 00 00 00`, not
  a dialect we must then test forever.

- **Offer 5.6, 5.7 or 5.8 instead.** The newest dialect, manifest
  handshake included. Rejected: nothing past 5.4 is probe-pinned — 5.6
  renames the notifications keys this ADR decides, 5.7 adds the manifest
  handshake, 5.8 adds LOGON SUCCESS `advertised_address` — so offering
  one is guessing at a contract. The ceiling moves with its own probe
  and ADR.

- **Implement the manifest-v1 handshake (F-06's literal text).** The
  manifest advertises a version and capability menu to 5.7+ clients.
  Rejected: every current driver sends the classic four proposals — the
  official driver's manifest marker sits beside three classic ones, so
  skipping it costs no client — and a two-version server's whole menu
  fits the classic form. Answering the marker would add a second
  handshake path (VarInt fields, capability bits) and re-pin
  negotiation-6, for no client that needs it. F-06 is resolved by this
  decision: the marker stays unanswered (ADR-0303).

- **Reply with the newest covered version regardless of client order.**
  A simpler selection function. Rejected: the probed rule is
  first-cover-wins in client order — Neo4j 2026.09 answers 4.4 to a
  4.4-first set while speaking 5.4 — and the handshake spec says
  proposals arrive in order of preference. Any other rule answers a
  version the client ranked below one it also offered.

## Consequences

- The offered set is data, not structure: ADR-0303's selection function
  generalizes to the two-version set with its typed `Negotiation`
  outcome and ADR-0141 deadline unchanged.
- The official Python driver (6.3.1) negotiates 5.4 against us; the
  driver smoke leg covers both negotiated versions.
- `docs/api/bolt/spec.md`'s Protocol line, message table and
  `docs/api/bolt/compatibility.md`'s F-06 entry update in the
  implementing change: "Bolt 5+ logon" retires from Not supported, and
  the manifest handshake moves from deferred to decided-not-implemented.
- The compat corpus (ADR-0304) gains 5.4 scripts — both reply orders,
  manifest-then-version, HELLO field validation, LOGON
  success/failure/DEFUNCT, LOGOFF, TELEMETRY, the notifications options,
  the element-id structs, the fixed DateTime forms — and its grammar
  gains the 5.x message names (LOGON, LOGOFF, TELEMETRY) and `!: BOLT
  5.4`, with `tests/compat/README.md` in the same change.
- A 4.4 connection is byte-identical to today: same reply, same HELLO
  auth and patch negotiation (ADR-0329), same legacy DateTime encoders.
  Every pinned baseline script keeps passing.
- No earlier ADR is reversed: ADR-0303's rule generalizes with the
  manifest never-match intact, ADR-0329's patch stays 4.4-only while
  its structures become
  the 5.x defaults, ADR-0126's schemes and resolution order move to
  LOGON unchanged, and ADR-0363's list is what the new keys filter.
- Raising the ceiling past 5.4, or lowering it past 4.4, is a new probe
  plus a new ADR; the deferred list shrinks, never grows.
